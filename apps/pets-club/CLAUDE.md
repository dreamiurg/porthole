# Pets Club — agent brief

## What this is

Pets Club is a touch-only, Tamagotchi-style dog companion for the Waveshare ESP32-S3-Touch-LCD-2.1, a round 480x480 capacitive-touch panel with no physical buttons. It is built for kids aged 5-10 who like reading and dogs: the pet grows over real calendar days, learns eight tricks over three lessons each, and is read twenty-plus original stories from a library that unlocks with daily gifts. Up to three kids can share one device as separate "houses," each with its own pet, room, and reading level. Everything renders into a 160x160 indexed-color framebuffer (32-color palette) that gets upscaled 3x to the physical panel. The pet never dies, never runs away, and never resets — stats decay toward floors, not through them.

It lives at `apps/pets-club/` in the porthole monorepo (apps for this board sharing build/test/deploy infrastructure). Every path below is relative to `apps/pets-club/`, and every command runs from there (or as `make -C apps/pets-club <target>` from the repo root). The shared PlatformIO board base is `../../platform/waveshare-round.ini`.

## Architecture map

`src/game/` is the platform-agnostic core. It compiles unchanged into both the firmware and the host simulator (`-DHOST_BUILD` only changes what `main()` exists, not the game logic):

- `pet.h` / `pet.cpp` — the simulation. Owns the `Save` struct (everything persisted), stat decay and floors, growth stages, gifts, stickers, trick progress, and the age-based reading-level/word-length tables. No rendering, no platform calls; this is what `host/test_pet.cpp` exercises directly.
- `game.h` / `game.cpp` — the screens. One `Game` class, a `Screen` enum, one `update`/`draw` pair per screen, input handling, toast/particle/sound selection, and save hand-off (`takeSave`/`takeErase`) back to whichever platform is hosting it.
- `gfx.h` / `gfx.cpp` — the renderer. A 160x160 indexed-color framebuffer (`gfx::fb`), drawing primitives, the 8x8 font, the round-mask test (`gfx::inCircle`), and the `UiAudit` hit-region log / text-box log that the `ui` sim command and the playtester agent read.
- `input.h` — turns raw touch samples into tap/long-press/drag edges (`InputTracker`); shared verbatim by firmware and host.
- `palette.h` — the fixed 32-color palette and the day/evening/night tint tables.
- `content.h`, plus its level-3 extensions `content_level3_books.h` and `content_level3_words.h` (see the note under constraint 2 below) — story text (`Book`) and spelling words (`WordClue`). Plain data, no logic.
- `sprites.h` — AUTO-GENERATED by `tools/art.py`. Never hand-edited; its own header says so.
- `font8x8_basic.h` — third-party public-domain font table, not normally touched.

`src/board.cpp`, `src/board.h`, `src/main.cpp` are the firmware. `board.h` is the hardware contract (display present/init, touch, RTC, backlight, buzzer, NVS blob storage); `board.cpp` implements it for this specific board; `main.cpp` is the Arduino `setup()`/`loop()` that wires `board::` to `Game`, times saves, dims the backlight, and parses serial commands.

`host/` is the simulator and the test: `sim.cpp` (SDL2 window, or headless `--script`/`--serve` modes) and `test_pet.cpp` (the pet-simulation self-check). Both link `src/game/*.cpp` directly; neither touches `board.cpp` or `main.cpp`.

`tools/` generates assets and dev tooling: `art.py` (parametric dog rig + ASCII icons -> `src/game/sprites.h` and `build/art/sheet.png`) and `webemu.py` (serves `build/host/snap --serve` in a browser).

## Hard constraints

Every change must respect all seven. None of these are stylistic; each one maps to a real failure mode (a save that bricks on the next boot, a button a kid can't reach, a dog that "dies").

1. **Round screen.** The visible area is the circle of radius 80 around (80,80) in logical px (`gfx::CX`, `gfx::CY`, `gfx::R` in `src/game/gfx.h`; test with `gfx::inCircle(x, y[, margin])`). 1 logical px = 3 physical px = 0.33 mm (160x160 logical -> 480x480 physical). Anything tappable must be at least 24x22 logical (8 mm) and lie entirely inside the circle — that is the exact size of the four home-screen buttons (`BTN_W=24, BTN_H=22` in `game.cpp`), not a rounded-up guideline. Text must never be cut by the bezel: before placing text at row `y`, compute the chord half-width `sqrt(80^2 - (y-80)^2)` and keep the text's full drawn width inside `[80 - halfwidth, 80 + halfwidth]`.
2. **32 colors, 7-bit ASCII only.** Every framebuffer pixel is a palette index 0-31 (`Col` enum, `src/game/palette.h`) or `C_T` (255, transparent, sprites only) — never a 33rd color or an out-of-palette blend. All text renders through the 8x8 font (`font8x8_basic.h`), which only covers ASCII 0-127: no curly quotes, no em/en dashes, no accented letters, anywhere a kid sees it (UI strings, story text, names).
3. **The buzzer is harsh.** `board::buzzer()` / `Game::soundOn()` drive a single-tone piezo. Never wire a sound to routine input (taps, navigation) — only to rare, meaningful moments (growth, a trick learned, a gift, a sticker, end of a minigame), and only through the existing `Sound` enum in `game.h`. There is a per-house mute toggle on the stats screen; every sound path must respect it.
4. **`Save` layout is append-only.** `Save` (`src/game/pet.h`) is persisted as a raw byte blob per house (`board::saveBlob`, NVS keys `s0`..`s2`). To add a field: put it immediately before `crc`, bump `SAVE_VERSION`, and extend `pet::loadBlob` so every older blob size/version still loads (see the `SAVE_V1_SIZE` migration path and its round-trip test in `host/test_pet.cpp` for the pattern the v1->v2 change already used). Never reorder or resize an existing field — that corrupts every save already written to a device, silently.
5. **The pet never dies.** Every stat decays toward a floor and stops (`pet::FLOOR_FOOD`, `FLOOR_FUN`, `FLOOR_ENERGY`, `FLOOR_CLEAN` in `pet.h`; currently 20/25/20/20) — no game over, no running away, no forced reset. Time away is capped at `pet::OFFLINE_CAP_SEC` (12 hours) of decay, and overnight hours count as sleep, so a weekend offline must never read as neglect.
6. **Built for a 5-10 year old.** Short, common, 7-bit-ASCII words. Failure is gentle: a wrong answer or a miss shows the right thing and moves on — it never blocks progress or resets state. No dead ends: every screen needs an always-reachable way back (`Game::drawBackButton`/`backButton` or an equivalent visible exit); check this for any new screen.
7. **Verify in the simulator before calling it done.** The physical device may be unplugged — that is not an exemption. Every gameplay or UI change needs at least one of: `make test` (pet-simulation self-check), `make snap` plus a script (see the `tour` skill), or `make playtest` (see Workflows below). No verification behind it means it is not done.

Note on constraint 1 and automated checks: `make playtest`'s UI audit only *fails* a run on a target smaller than 18 logical px (6 mm) — it *warns* (non-blocking) anywhere from 18 up to the real 24x22 (8 mm) floor. A WARN-severity "target size" finding is still a constraint violation; treat it as one, don't wait for it to become a FAIL.

Note on constraint 2 and content: level-3 stories and words live in `src/game/content_level3_books.h` and `src/game/content_level3_words.h`, pulled into `content.h` via `#if __has_include(...)`. The include guard string has to match the filename exactly — a mismatch compiles the extension out with no error, no warning. `tools/check_content.py` re-renders every string through the real 8x8 font and word-wraps it into the exact box the game draws it in; see the `new-story` skill.

## Workflows

### make targets (Makefile)

The repo root and CI call these by name; keep them working:

- `make lint` — app-specific static checks: `tools/check_content.py`, `tools/art.py --check`, and a `-Werror` host build of the game + sim. (ruff and shellcheck run from the repo-root pre-commit, not here.)
- `make check` — `lint` + `test`. What pre-commit runs; a few seconds.
- `make ci` — `check` + `playtest` + `coverage`: everything CI runs for this app except the firmware build.
- `make coverage` — builds `test_pet` and `snap` with `--coverage` under `build/coverage/`, runs `test_pet` plus the non-monkey playtests, and writes line coverage of `src/game/*.cpp` to `build/coverage/coverage.xml` (Cobertura, via gcovr). Fails below `COV_MIN` in the Makefile. On macOS gcovr uses `xcrun llvm-cov gcov`; elsewhere `gcov`. Uses `gcovr` from PATH, else `uvx gcovr`.
- `make firmware` / `make flash [PORT=...]` / `make monitor [PORT=...]` — `pio run -e firmware`, upload, and the 115200-baud serial monitor. PlatformIO auto-detects the port when `PORT` is not given.

Development targets:

- `make sim` — SDL2 window. Mouse = finger. Keys: `h` +1 hour, `n` +8 hours, `d` +1 day, `r` reset save, `s` screenshot to `build/host/shot.bmp`, `p` print stats to stdout, `q`/Esc quit.
- `make snap` — headless binary, no SDL, two modes:
  - `./build/host/snap --script FILE` runs a command script (see the `tour` skill) and writes named `.bmp` files to `build/host/`.
  - `./build/host/snap --serve` speaks the stdin/stdout protocol `tools/webemu.py` drives.
  - Both accept `--now EPOCH` (fixed clock) and `--fresh` (wipe saves first); the default clock is a fixed Tuesday 16:00 local time, so unscripted snapshots are still deterministic.
- `make snap-asan` — the same headless binary built with AddressSanitizer + UBSan. Used by the chaos-monkey playtest scenarios; slower, build it only when you need sanitizer coverage.
- `make test` — builds `host/test_pet.cpp` against `src/game/*.cpp` (minus `game.cpp`) and runs it immediately. Pure simulation self-check, no rendering. Must stay green.
- `make webemu` — depends on `snap`; runs `tools/webemu.py`, serves the game at `http://127.0.0.1:8765` (`python3 tools/webemu.py 8766` for another port). The buttons under the canvas skip time and force debug states for testing.
- `make art` — runs `tools/art.py`, regenerates `src/game/sprites.h` and, if Pillow is installed, `build/art/sheet.png`. `python3 tools/art.py --check` verifies `sprites.h` is current without rewriting it.
- `make playtest` — depends on `snap` and `snap-asan`; runs `python3 tools/playtest.py` against every scenario in `tests/playtests/*.txt`, writes `build/playtest/report.md` plus a contact-sheet PNG per scenario. See the `playtest` skill for how to read the report.
- `make clean` — removes `build/` (not `.pio/`, the firmware build cache).

### Firmware build and flash

```bash
make firmware                                  # pio run -e firmware
make flash                                     # or: make flash PORT=/dev/cu.usbmodemXXXX (Linux: usually /dev/ttyACM0)
make monitor
```

`platformio.ini` extends `[waveshare_round]` from `../../platform/waveshare-round.ini` (platform pin, board, PSRAM and USB flags) and adds only the app specifics (partition table, upload speed, warning flags, `-Isrc/game`). The env is `firmware`.

See the `flash` skill for the PlatformIO-venv Python-dependency caveat and how to set the clock.

### Serial commands (`main.cpp` `loop()`, 115200 baud)

| Command | Effect |
| --- | --- |
| `S` | Print stats (`Game::debugPrint()`) plus free heap and current epoch |
| `T<epoch>` | Set the RTC and running clock to `<epoch>` (local wall-clock seconds; ignored if <= 1,600,000,000) |
| `R` | Erase every house and reboot |
| `P<n>` | Clear house `n`'s 4-digit secret code (parent escape hatch) |
| `D` | Toggle touch-position logging |

### Hooks and CI

Hooks are managed by the repo-root pre-commit config, not by this app: it runs ruff and shellcheck repo-wide and `make -C apps/pets-club check` for this app. CI runs `make ci` plus the firmware build. Run `make ci` yourself before pushing anything that touches gameplay or UI; a red CI run is a worse time to find out.

### Skills

Project skills live under the repo-root `.claude/skills/` (agents under `.claude/agents/`), with paths written as `apps/pets-club/...`: `playtest`, `flash`, `art`, `new-story`, `tour`. Each is a short, imperative how-to for its workflow. Load the matching skill instead of re-deriving the steps.

## Model policy

**opus** for anything that writes or reviews code, or judges design/polish: `game-designer`, `game-engineer`, `firmware-engineer`, `pixel-artist`, `playtester`, `reviewer`.
**sonnet** for prose and bounded research: `story-writer`.
**haiku** for mechanical sweeps (renames, formatting, single-file lookups) — no standing agent above is haiku; reach for it directly, ad hoc, for that class of task.

State the model when dispatching an agent (for example: "dispatching `game-engineer` (opus) to implement this"). Between sonnet and opus for anything code-shaped, take opus.
